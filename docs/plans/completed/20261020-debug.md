# `wavo debug`

Done: 2026-10-20, PR #58

A diagnostic report users paste into issues, which also tells us how to tune kernels per machine
class, modelled on `macmon debug`: a one-line header, `--- Section ---` dividers, aligned
`key value` rows, `error=…` where a part fails and the report goes on. Approved by the person as
`debug` (the design called it `info`).

## Design

- **Header:** `wavo <version> | OS: <os> | <arch>`. CI's dev builds already carry the
  `git describe` version (vladkens/actions `dev-version`), so no build script.
- **Machine:** model, CPU (cores, Apple's P/E split), memory, Apple GPU cores. macOS via
  `sysctl` and `ioreg`, Linux via `/proc`, `/sys`, `os-release` and `lscpu` (ARM cores),
  Windows via one PowerShell call. No new dependency. The CPU's SIMD features (runtime
  detection) and the code path of the decoders' matrix products, from `src/cpu.rs` itself
  through a hidden `wavo::cpu_path()`.
- **GPU:** every adapter wavo can reach (Vulkan, Metal, DX12), the one `Model::load` picks
  first: name, API, kind, driver, PCI ids, the kernel tier and why not a faster one, then the raw
  facts the tiers depend on (subgroups, shader-f16, cooperative matrices, passthrough, mappable
  buffers, workgroup and buffer limits, immediates). `WGPU_*` variables when set.
- **Models:** the cache with what set it, and the downloaded models with their sizes.
- **Warnings** at the end: a software adapter (llvmpipe, lavapipe, WARP) in use, and on Linux
  then no `/dev/dri/renderD*` or none the user may open. `wavo run` prints the same
  software-adapter line on stderr.
- **No probes:** only adapter info and features are read; no device is created and no kernel
  compiles, since a broken driver can crash there (AMD 25.10 on 16×16 matrices).
- **Library:** `wavo::devices()` (the adapters, `Model::load`'s first) and `Device::kernels`
  with a `#[non_exhaustive]` `Kernels` enum (`Portable`, `Matrix8`, `Matrix16`, `Tensor`): the
  tier rule stays in `src/gpu/` and isn't copied into the CLI. From `devices()` the tier the
  features allow; from `Model::device()` the GEMM's tier after its probe. `Device`'s `Display`
  is unchanged. Raw wgpu features and limits stay CLI-only.
- No `--json`: the text is what users paste, and a JSON format would be another promise and ~50
  more CLI lines over the budget.

## Result

`wavo debug` creates no device and runs no probes. The M2 shows `8x8 matrices: the tensor GEMM
is for Apple M5 / A19 and newer`; the N100's Intel iGPU `portable: no cooperative matrices`,
with llvmpipe listed as a second adapter. With llvmpipe forced, `wavo debug` and `wavo run` both
warn `llvmpipe (LLVM 20.1.2, 256 bits) is a software GPU, emulated on the CPU: expect 10-50x
slower transcription`, as the Ubuntu ARM64 VM does on its own. The M5 shows the tensor tier; the
Windows laptop the RTX 4060 on 16×16 matrices, the Radeon 610M `portable: 16x16 matrices run on
NVIDIA only so far`, and DX12 `no subgroup barriers, cooperative matrices`. ~50 ms on the M2 and
the N100, ~3 s on Windows (DX12 adapters are slow to enumerate). CLI code ~645 → ~965 lines
without tests.
